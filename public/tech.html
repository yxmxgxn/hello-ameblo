仕組み

ハロー！プロジェクトのメンバーのアメブロを、本文から横断検索できるようにした個人サイトです。 どうやって記事を集め、何を保存し、何をしないと決めているかを説明します。

1. 全体の作り

サイトは Cloudflare Workers と D1（SQLite）で動いています。 巡回プログラムは GitHub Actions で1時間ごとに動き、アメブロの記事を読んで D1 に入れます。 検索のたびにアメブロへ問い合わせることはありません。

D1 に保存しているのは、記事ごとに次のものです。

  • タイトル・投稿日時・テーマ・編集日時・公開状態
  • 本文のテキスト。記事のHTMLから文字だけを取り出したもので、画像・リンクカード・埋め込みは含みません
  • 本文とタイトルから作った検索用の索引（2. を参照）

本文のテキストは、検索結果に一致した箇所の前後を出すために使います。画面やAPIで全文を返すことはありません（3. を参照）。

どのブログ・どのテーマが誰の記事かは、手で管理している対応表で決めています。 対応表を直すと、次の巡回で取り込み済みの記事の書き手も直ります。

構成

GitHub Actions（巡回, Python）
   │  Bearer 認証の HTTPS
   ▼
Cloudflare Worker  ── /api/crawl/*（巡回専用）
   │                 /api/search ほか（公開 API）
   ▼
D1（SQLite）  ◀── 静的ファイル（HTML / JS / CSS）も同じ Worker から配信
  • 巡回プログラムは、読んだ記事を Worker の巡回専用 API に渡します。D1 へ直接は書きません。索引の作り方を、Worker の1か所に保つためです。
  • 巡回専用 API は、トークンを持たない呼び出しには「存在しない」ことにして 404 を返します。
  • 公開 API は、同じ IP からの呼び出しを1分あたり120回に制限しています。
  • 巡回の起動は、Worker の Cron Trigger（毎時7分）が GitHub の workflow_dispatch を呼んで行います。GitHub の schedule は、混んでいるときに遅れたり飛ばされたりしたためです。

テーブル

テーブル役割
entries記事。主キーはアメブロの記事番号（時系列で増える）。タイトル・本文テキスト・投稿日時・テーマ・メンバー番号・編集日時・公開状態などを持つ
entry_fts全文検索の索引（FTS5、rowid = 記事番号）。本文そのものではなく、2文字ずつ区切った文字列だけを持つ（contentless）
targets「どのブログ・どのテーマが誰か」の対応表。手で管理しているスプレッドシートから、巡回のたびに丸ごと作り直す
blogs / checksブログごとの巡回の進み具合。新着の取り込み位置と、削除チェックの位置
members / member_meta / groupsメンバー名、所属グループ、現役かどうか
member_blogsメンバーごとの、記事があるブログ。「ブログで絞る」の候補に使う

テーマの付いていない記事や、1つのブログに複数人が書く場合の割り当ては、例外の表で別に持ち、巡回のたびに取り込み済みの記事へ反映します。

2. 検索のしかた

形態素解析（単語への分割）は使わず、本文を2文字ずつ区切った索引で引いています。 辞書に載らない固有名詞・当て字・口語にも強く、入力した文字列がそのまま並んでいる記事を探す「部分一致」に近い動きになります。

  • 全角・半角、英字の大文字・小文字は区別しません
  • 記号・句読点・改行・絵文字は無視します。「りんご飴」で「りんご、飴」も見つかります
  • 空白で区切ると、すべての語を含む記事に絞り込みます（最大5語・100文字）
  • 語の前に「-」を付けると、その語を含まない記事に絞り込みます。含まない語だけでは探せません
  • 漢字は1文字でも検索できます。ひらがな・カタカナ・英数字の1文字だけでは検索しません（ヒットが多すぎるため）

結果は新しい記事から順に並びます。総ヒット件数は表示しません。 数えるだけで検索そのものより重くなるためです。 長すぎる検索語や記号だけの検索語は、黙って切ったり無視したりせず、理由を画面に出します。

索引の作り方

  1. 本文とタイトルを正規化します。NFKC で全角・半角をそろえ、小文字にし、日本語（かな・漢字・々・〆）と英数字以外を取り除きます。
  2. 正規化した文字列を、2文字ずつ区切ります。「宮本佳林」なら「宮本 本佳 佳林」です。
  3. この文字列を FTS5 に入れます。

検索語も同じ正規化をして2文字ずつに区切り、連続したフレーズとして照合します。 索引と検索で正規化が食い違うとヒットしないので、同じ関数を使っています。 空白で区切った語は AND で繋ぎ、語の前の - は NOT にします。 FTS5 の NOT は「何かを含む集合から除く」形なので、含む語が無いと使えません。 1文字の語は、漢字だけ「その字で始まる2文字」の前方一致にします。

3. 表示するもの

検索結果には、一致した箇所の前後40字ほどだけを出します（1記事につき最大2か所）。 保存している本文のテキストから切り出すので、絵文字や記号は元の本文のまま表示します。 記事を読むときは ameblo.jp の元記事へ移動します。このサイトの役目は、元記事を見つけて送り届けることです。

検索結果や新着一覧は、ページを開いたあとに API（/api/）から読み込んで描いています。 robots.txt で /api/ を検索エンジンに読ませないようにしているので、抜粋が検索エンジンに載ることはありません。 API の応答にも noindex を付けています。

重くしないための工夫

  • 公開 API の結果は、次の毎時20分まで、Cloudflare のキャッシュに載せます。巡回が入れ替える時刻に合わせています。
  • 語なしで1つのブログを見る一覧は、(blog, published) の索引で読みます。索引が無いと、そのブログの記事を全部読んでから並べ替えるため、5秒近くかかっていました。
  • メンバーやブログを指定した検索は、その人の記事を基準にヒットを確かめます。

4. アメブロへの配慮

  • 読み込みは1秒に1回まで。並列では取りに行きません
  • 巡回プログラムであることと、このサイトのアドレスを User-Agent で名乗っています
  • 1回の巡回の時間とリクエスト数に上限を設け、上限に達したら次の回に回します
  • 記事一覧で分かることは一覧だけで済ませ、記事ページはなるべく開きません
  • 初回の取り込みは数日かけてゆっくり進めました。急ぐ理由がないからです
  • いまは、新着の取得と、編集・削除を反映するための記事一覧の見回り（5. を参照）だけをしています

巡回の設計

  • 新着: ブログごとに、記事一覧 API を新しい方から読み、取り込み済みの最新の記事番号より新しいものだけを取ります。
  • 見回り: 取り込み済みの記事を、記事一覧の順に読み直します。毎時25ページ分ずつ進め、全体で30日ほどで一周します。
  • 1日1回: 日本時間の4時台に、各ブログの新しい方の数ページと、30日以上書いていないブログの新着を見ます。
  • Worker への通信が切れたり時間切れになったりしたときは、やり直します。一度の切断で、巡回全体が止まらないようにするためです。

本文は、記事ページの HTML から文字だけを取り出して作ります。スクリプト・スタイル・iframe・SVG と、リンクカード・X・Instagram の埋め込みは除き、ブロック要素の切れ目は改行にします。

5. 編集・削除への追従

取り込み済みの記事も、記事一覧を順番に読み直して見直しています（全ブログを一周するのに30日ほどかかります）。 一覧に載っている編集日時が変わっていたら、その記事の本文を取り直し、索引も入れ替えます。

削除・非公開になった記事は、このサイトからも消します。 ただし、以前、アメブロには残っている記事を「無くなった」と取り違えて消してしまったことがあったため、巡回が記事を自動で消すことはありません。

  1. 見回りで、一覧にあるはずの範囲に記事が無い、またはページが 404・非公開と返ってきたときは、その記事に印（gone_since）を付けるだけにします。消しません。
  2. 1ページの見回りで印を付けようとした記事が5件を超えたら、異常とみなして印も付けません。アメブロ側の不調や、こちらの取得の失敗を、削除と取り違えないための安全弁です。
  3. 印を付けたときは、記事のIDとあわせて、運営者の Discord に通知します。
  4. 運営者が、実際にアメブロで見て確かめ、「消してよい」ものだけを、手動の実行で削除します。印が付いていない記事は、この手順では消せません。
  5. 印を付けたあとの見回りで、記事が見つかったら、印を外します。

もし誤って消してしまっても、一覧にあって、こちらに無い記事は、次の巡回で取り込み直されます。 急いで戻したいときのために、記事を指定して取り込む手動の実行も用意しています。

6. わかっている制約

  • ひらがなとカタカナは別扱い。「りんご」で「リンゴ」は出ません。書き分けを潰したくないので、このままにしています
  • アクセント付きのラテン文字は落ちます（「Café」は「caf」として扱われます）
  • 並びは公開日時の順です。ただし検索語を入れたときは、記事番号の順に100件ずつ読み、その100件の中を公開日時で並べ替えています（全部のヒットを公開日時で並べると重すぎるため）。予約投稿の記事や、投稿日時をあとから過去の日付に変えた記事は、100件の区切りをまたいで前後することがあります（数分から数日）
  • グループブログで、テーマが付いていない記事などは書き手を決められず、メンバーでの絞り込みに出ないことがあります
  • 記事の末尾に毎回付くお知らせなどの定型文も、本文として扱っています。お知らせの言葉で検索すると、多くの記事がヒットします。どこからが定型文かを機械で決めると本人の文章まで消してしまうおそれがあるので、いまは外していません

7. 取らない・やらないと決めたこと

  • 画像・動画は1バイトも保存しない。文字だけです
  • アメンバー限定記事は取りに行かない。公開されている記事だけを読む
  • ブロガーが「検索エンジンに載せない（noindex）」にしているブログは取り込まない。取り込み済みの分も消す
  • 本文中のリンクカード（OGPカード）や X・Instagram の埋め込みは除く。リンクカードには、リンク先のページのタイトルや説明文が入っていて、画面に表示しきれない部分まで記事のデータに含まれていることがあります。本人が書いた文章ではないので、検索の対象にしていません。そのため、アメブロの検索ではヒットする記事が、このサイトではヒットしないことがあります
  • 本文の全文は画面に出さない
  • 記事の本文をAIで処理しない。要約・文章の生成・学習には使わない（プログラムを書くのにはAIを使っています）
  • 誰の記事か決められないものに、推測でメンバーを割り当てない
  • 並列での取得や、取得間隔の短縮はしない

消してほしい・載せないでほしいという連絡があれば、そのとおりに対応します。 ご連絡は、このサイトについてのページ下にあるフォームから送ってください。 確認しているAmebaの決まりごとも、そのページの最後に載せています。

8. 試しているもの

アメブロの公式 RSS は、更新を知らせるハブ（WebSub）を宣言しています。 これを使うと、新着を、巡回を待たずに知れる可能性があります。更新のないブログを見に行かずに済み、アメブロへのアクセスも減らせます。 いまは、一部のブログで、通知が実際に届くか、どれくらい速いかを確かめている段階です。結果が出たら、ここに書きます。
