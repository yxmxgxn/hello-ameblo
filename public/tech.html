ハロプロ アメブロ検索

仕組み

このサイトについて ｜ 検索に戻る

ハロー！プロジェクトのメンバーとOGのアメブロを、日付と本文から探せるようにした個人サイトです。 どうやって記事を集め、何を保存し、何をしないと決めているかを説明します。

1. 全体の作り

サイトは Cloudflare Workers と D1（SQLite）で動いています。 記事は前もって集めてこのサイトのデータベースに入れてあり、検索のたびにアメブロへ問い合わせることはありません。 日付の索引と、本文から作った検索用の索引を先に作っておき、1回に100件だけを引くので、件数が増えても速さを保てます。

どのブログ・テーマが誰の記事かは、同じ作者のサイト（karin-archive）の「SNS一覧」の元になっている表で決めています。 表を直すと、次の収録から対象も変わり、取り込み済みの記事の書き手も付け直されます。

データの流れ

  1. 対応表：どのブログ・テーマが誰のものかを、上の表から読みます
  2. 収録プログラム（GitHub Actions・毎時）：アメブロの記事一覧と記事ページを読み、本文のテキストを取り出します
  3. Worker：合言葉つきのクローラ用APIで受け取り、本文を2文字ずつに区切った索引にして書き込みます
  4. D1（SQLite）：記事と、検索用の索引（FTS5）を持ちます
  5. あなたのブラウザ：検索のAPIが、一致した箇所の前後だけを返します。記事を読むときは、アメブロの元の記事へ移ります

保存しているもの

D1 に保存しているのは、記事ごとに次のものです。

  • タイトル・投稿日時・テーマ・編集日時・公開状態
  • 本文のテキスト。記事のHTMLから文字だけを取り出したもので、画像・リンクカード・埋め込みは含みません
  • 本文とタイトルから作った検索用の索引（3. を参照）

本文のテキストは、検索結果に一致した箇所の前後を出すために使います。画面やAPIで全文を返すことはありません（4. を参照）。

2. 記事の集め方

アメブロのページ（ameblo.jp）を、公開されているとおりに読んで集めています。 収録プログラムは1時間ごとに動き、新着の取得 → 編集・削除の見回り → 過去の記事の遡りの順に進めます。

ブログと書き手の対応

  • 個人ブログは、ブログ丸ごとその人の記事にします
  • グループの公式ブログは、テーマごとに誰の記事かを対応させます
  • 対応表で決められない記事は、例外を書いたファイルで決めます（「このテーマは取り込まない」「この記事はこの人のもの」など）。題名の末尾の署名を手がかりに、書き手を振り分けるものもあります
  • 誰の記事か決められないものに、推測でメンバーを割り当てることはしません。書き手を空欄のまま取り込み、メンバーでの絞り込みには出しません

新着と、過去の記事

  • 新着：各ブログの記事一覧を1ページ目から読み、取り込み済みの最新より新しい記事を取ります。予約投稿は、書き始めた時点の番号が付くので、あとから公開されると古い番号で一覧の上の方に出てきます。番号だけで見ると取りこぼすので、読んだページの記事は、取り込み済みかどうかを全部確かめます
  • 過去の記事：新着で使わなかった分の時間で、1ページ（20件）ずつ古い方へ遡ります。全ブログを1ページずつ順番に回るので、全員が少しずつ埋まっていきます。端まで届いたブログは完了です
  • 30日以上書いていないブログは、新着の確認を1日1回にしています
  • 新しく対象になったブログは、過去の記事がそろうまでにしばらくかかります

アメブロへの配慮

  • 読み込みは1秒に1回まで。並列では取りに行きません
  • 巡回プログラムであることと、このサイトのアドレスを User-Agent で名乗っています
  • 1回の収録の時間（50分）とリクエスト数（3000回）に上限を設け、上限に達したら次の回に回します
  • 記事一覧で分かることは一覧だけで済ませ、記事ページは、新しい記事・編集された記事・消えたかもしれない記事だけ開きます
  • 初回の取り込みは数日かけてゆっくり進めました。急ぐ理由がないからです

編集・削除への追従

  • 編集：記事一覧にある編集日時が、こちらの記録と違っていたら、その記事の本文を取り直し、索引も入れ替えます。編集日時は一覧に載っているので、確かめるだけでは記事を開きません
  • 削除：一覧から消えている記事を見つけたら、その記事のページだけを開いて確かめます。「見つからない」とはっきり分かったものは、自動では消さず、印を付けて作者に知らせます。作者が確かめて、消すかどうかを決めます
  • 通信の失敗やアメブロ側の一時的な不調を、削除と取り違えないよう、確かめられなかったものは何もせず、次の見回りに回します
  • 見回りは、全ブログを一周するのに1か月ほどかかります。そのほかに、1日1回、各ブログの新しい方の数ページを読み直します（編集・削除は、たいてい新しい記事で起きるためです）

3. 検索のしかた

形態素解析（単語への分割）は使わず、本文を2文字ずつ区切った索引で引いています。 辞書に載らない固有名詞・当て字・口語にも強く、入力した文字列がそのまま並んでいる記事を探す「部分一致」に近い動きになります。

  • 全角・半角、英字の大文字・小文字は区別しません
  • 記号・句読点・改行・絵文字は無視します。「りんご飴」で「りんご、飴」も見つかります
  • 空白で区切ると、すべての語を含む記事に絞り込みます（最大5語・100文字）
  • 語の前に「-」を付けると、その語を含まない記事に絞り込みます。含まない語だけでは探せません
  • 漢字は1文字でも検索できます。ひらがな・カタカナ・英数字の1文字だけでは検索しません（ヒットが多すぎるため）

結果は新しい記事から順に並びます。総ヒット件数は表示しません。 数えるだけで検索そのものより重くなるためです。 長すぎる検索語や記号だけの検索語は、黙って切ったり無視したりせず、理由を画面に出します。

4. 表示するもの

検索結果には、一致した箇所の前後40字ほどだけを出します（1記事につき最大2か所）。 保存している本文のテキストから切り出すので、絵文字や記号は元の本文のまま表示します。 記事を読むときは ameblo.jp の元記事へ移動します。このサイトの役目は、元記事を見つけて送り届けることです。

検索結果や新着一覧は、ページを開いたあとに API（/api/）から読み込んで描いています。 robots.txt で /api/ を検索エンジンに読ませないようにしているので、抜粋が検索エンジンに載ることはありません。 API の応答にも noindex を付けています。

5. わかっている制約

  • 消された記事は、すぐには消えません。見回りで見つからなかった記事を、作者が確かめてから消します。確かめるまでは、検索に残ります（リンク先は開けません）
  • 書き直しは、見回りのときにそろいます。新しい記事は毎日見直しますが、古い記事は一周するのに1か月ほどかかるので、それまでは前の本文のままのことがあります
  • ひらがなとカタカナは別扱い。「りんご」で「リンゴ」は出ません。書き分けを潰したくないので、このままにしています
  • アクセント付きのラテン文字は落ちます（「Café」は「caf」として扱われます）
  • 並びは公開日時の順です。ただし検索語を入れたときは、記事番号の順に100件ずつ読み、その100件の中を公開日時で並べ替えています（全部のヒットを公開日時で並べると重すぎるため）。予約投稿の記事や、投稿日時をあとから過去の日付に変えた記事は、100件の区切りをまたいで前後することがあります
  • グループブログで、テーマが付いていない記事などは書き手を決められず、メンバーでの絞り込みに出ないことがあります
  • 記事の末尾に毎回付くお知らせなどの定型文も、本文として扱っています。お知らせの言葉で検索すると、多くの記事がヒットします。どこからが定型文かを機械で決めると本人の文章まで消してしまうおそれがあるので、いまは外していません

6. 取らない・やらないと決めたこと

  • 画像・動画は1バイトも保存しない。文字だけです
  • 本文の全文は画面に出さない
  • アメンバー限定記事は取りに行かない。公開されている記事だけを読む
  • コメントや読者の情報など、記事以外のものは取らない
  • ブロガーが「検索エンジンに載せない（noindex）」にしているブログは取り込まない。取り込み済みの分も消す
  • 本文中のリンクカード（OGPカード）や X・Instagram の埋め込みは除く。リンクカードには、リンク先のページのタイトルや説明文が入っていて、画面に表示しきれない部分まで記事のデータに含まれていることがあります。本人が書いた文章ではないので、検索の対象にしていません。そのため、アメブロの検索とは、結果が違うことがあります
  • 記事の本文をAIで処理しない。要約・文章の生成・学習には使わない（プログラムを書くのにはAIを使っています）
  • 誰の記事か決められないものに、推測でメンバーを割り当てない
  • 並列での取得や、取得間隔の短縮はしない
  • 検索した言葉やアクセスの記録を取らない

消してほしい・載せないでほしいという連絡があれば、そのとおりに対応します。 ご連絡は、このサイトについてのページ下にあるフォームから送ってください。 確認しているAmebaの決まりごとも、そのページの最後に載せています。

7. 技術の詳細

ここからは、作りを知りたい人向けの、細かい話です。このサイトが公開している範囲の説明で、鍵や合言葉は含みません。 このリポジトリの README.md にも、取得のまとめがあります。

構成

  • 画面：HTML・CSS・JavaScript のファイルを、Cloudflare Workers の Static Assets で配信しています。フレームワークは使っていません
  • API：同じ Worker が、/api/search（記事の検索）・/api/calendar（月・日ごとの件数）・/api/members（メンバーとグループ、収録の状況）・/api/day（その日の記事）を返します。同じ条件の結果は、データが変わる毎時の収録が終わるころ（毎時20分）まで、Cloudflare のキャッシュに置きます。同じIPアドレスから1分に120回を超えて呼ぶと、止めます
  • データ：Cloudflare D1（SQLite）です。entries（記事）、targets（ブログ・テーマと書き手の対応）、blogs（ブログごとの取得の進み）、checks（見回りの進み）、entry_fts（検索用の索引）が中心です
  • 収録：GitHub Actions のワークフロー（Python）で、起動は Cloudflare の定時実行（Cron Triggers）が毎時行います。GitHub の定時実行は、混んでいると遅れたり飛んだりしたためです。結果は、Worker のクローラ用のAPIに送ります。クローラ用のAPIは、合言葉（Bearer 認証）が無いと使えません
  • メンバーごとのページ：/?m=番号 を開くと、Worker が HTML を書き換えて、その人用のタイトル・説明文・canonical・パンくずを付けて返します。ページは1枚のままです。サイトマップにも載せています

アメブロのページの読み方

ブログの記事一覧（2ページ目からは entrylist-2.html のように番号が付きます）と、記事のページを読みます（<…> は入れ替わる部分です）。 

GET https://ameblo.jp/<ブログID>/entrylist.html
GET https://ameblo.jp/<ブログID>/entry-<記事番号>.html
  • どちらのページにも、window.INIT_DATA という名前で JSON が埋め込まれています。一覧は20件ずつ、タイトル・投稿日時・テーマ・編集日時・公開状態が分かります（本文は無し）。本文は、記事のページを1件ずつ読むしかありません
  • 本文は、記事の HTML から文字だけを取り出します。リンクカード・X や Instagram の埋め込み・スクリプトは除き、改行は段落や <br> から作り、連続する空白は詰めます
  • 記事番号（entry_id）は、アメブロが時系列で付けているものをそのまま記事のIDにします
  • 一覧のページにある robots の noindex で、ブロガーが検索エンジンに載せない設定にしているかを読みます
  • 見つからない（404・410）以外のエラーは、間をあけて3回までやり直します

取る順番と、上限

  • 1回の収録は、新着 → 編集・削除の見回り → 遡りの順で、時間と回数を使います
  • 上限は、1秒に1回・最大50分・最大3000リクエストです。上限に達したら、続きは次の回に回します。進み具合は D1（blogs と checks）に持っているので、収録プログラムは何も覚えていなくても続きから進めます
  • 新着：取り込み済みの最新の記事番号より新しいものを、一覧の1ページ目から取ります
  • 見回り：1回の収録で、一覧を25ページずつ読み直します。そのほかに、1日1回（日本時間の4時台）、各ブログの新しい方の3ページを読み直します
  • 遡り：見回りで使わなかった分の時間で、過去の記事を1ページ（20件）ずつ、古い方へたどります
  • D1 の上限（容量・1日の書き込み数）に当たったら、失敗にはせず、その回はそこで終えて、次の回に続けます

消えたかもしれない記事の見つけ方

  • 見回りは、記事一覧を1ページ目から順に読み直し、「前のページの一番古い記事番号」から「このページの一番古い記事番号」までのあいだにあるはずなのに、一覧に無い記事を探します。範囲を記事番号でつなぐので、途中で新着が増えてページがずれても、確認漏れが出ません
  • 一覧に無い記事は、その記事のページを開いて確かめます。404・410、または公開状態が「公開」でないときだけ「見つからない」とします。ページは開けたのに記事のデータが読めないときや、通信が失敗したときは、確かめられなかったものとして、何もしません
  • 「見つからない」記事には、印（gone_since）を付けて、作者に知らせます。自動では消しません。検索には残したまま、作者が確かめて、GitHub Actions を手動で実行して消します（印の付いていない記事は、指定しても消えません）
  • 1ページ（20件）で、5件を超えて見つからないときは、アメブロ側の不調や取得の失敗とみなして、印も付けません
  • 印を付けたあとで一覧に戻っていたら、誤検知として、印を外します
  • 編集の確認は、一覧の編集日時（last_edit_datetime）と、こちらの記録を比べます。記録が空の記事（日時を記録し始める前に取り込んだもの）は、日時だけを書き足し、本文は取り直しません

保存と、検索の索引

  • 記事は、アメブロの記事番号をそのまま主キーにして entries に入れます。取り込み済みの記事がもう一度送られてきたとき（編集）は、検索の索引の行を消して、書き直します。1回の取り込みは、50件までです
  • 検索用の索引（entry_fts、SQLite の FTS5）には、タイトルと本文を2文字ずつに区切ったもの（bigram）を入れます。中身そのものは持たず、索引だけを持つ形（contentless）にして、容量を節約しています
  • 文字は、NFKC で全角・半角をそろえ、小文字にして、ひらがな・カタカナ・漢字・英数字以外を除いてから区切ります。索引を作るときと、検索のときで、まったく同じ関数を使います。2文字に区切る処理は Worker だけで行い、実装が2つに分かれないようにしています
  • 検索語は、語ごとに2文字ずつのフレーズにして、MATCH で引きます。空白で区切った語は AND、「-」を付けた語は NOT で組み合わせます（例：りんご -飴 は ("りん んご") NOT ("飴" *)）。漢字1文字だけの語は、その字で始まる2文字の並びの前方一致にします
  • 日時は、日本時間の文字列（2016-03-05T21:00:00.000+09:00）で持ちます。年・月・日の絞り込みは、この文字列の前方一致と大小比較です

検索を速く保つ工夫

  • 語があるときは、検索の索引を外側にして、記事番号の順に、100件で打ち切ります。ヒットが多い語でも、全部は読みません
  • メンバーやブログを選んでいるときは、逆にその人の記事を順に読み、ヒットした記事の集合に入っているかだけを見ます。よく出る語で、あまり書いていない人を選んでも、ほかの人の記事を延々と確かめずに済みます（以前は、1回の検索で15万行ほど読んで、2秒近くかかることがありました）
  • 語が無く、2人以上を選ぶとき（メンバーの複数選択・「ハロプロ現役のみ」）は、1人ずつ公開日時の順に先頭から101件だけ読んで、混ぜ合わせます。読む行は、人数×101行で済みます（以前は、5万〜13万行を読んで、2秒前後かかっていました）
  • 続きは、最後に返した記事の位置（カーソル）から読みます。何ページ目でも、読み始める位置を直接引けます
  • 語が無く、1つのブログだけで絞るときは、（ブログ, 公開日時）の索引で、そのまま公開日時の順に読みます（この索引が無かったころは、そのブログの記事を全部読んでから並べ替えていて、5秒近くかかりました）
  • 総ヒット件数は数えません。結果は、毎時20分までキャッシュします

表示

  • 検索結果の抜粋は、保存している本文から、一致した箇所の前後40字（1記事2か所まで）を、そのつど切り出します。正規化で消えた文字（記号など）があるので、元の本文との対応表を作って、元のままの文字で表示し、一致した語に色を付けます。絵文字（2つで1文字の並び）の途中では切りません
  • 検索結果や新着は、ページを開いたあとに /api/ から読み込んで描きます。/api/ は、robots.txt で検索エンジンに読ませず、応答にも noindex を付けています
  • 記事への移動は、アメブロの元の記事へのリンクです。このサイトは、全文を返しません
